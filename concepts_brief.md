# Tiny-R-90M Repurpose + Docker + GHCR
* **Author:** egm-synthesizer (swarm blocked: all 6 lenses `not run`, brief compiled by direct inspection of README, Makefile, pyproject, both YAML configs, `model.py`, `config.py`, `train.py`, `ci.yml`)
* **Date:** 2026-11-10

## Overview
Change this repo from training the 3-billion-parameter Falcon-H1-3B-Instruct model to training the 90-million-parameter Falcon-H1-Tiny-R-90M model. Keep the same seven cyber-security datasets. Add new settings files for the small model, add a Docker container file so the same setup runs on a laptop, a Colab T4, and a rented RTX 3090 machine, and make GitHub build and upload that container automatically. Done means: a 5-step trial runs on a T4, a full training run finishes on a 3090 without the loss going to NaN or infinity, evaluation finishes without NaN, and mandatory GGUF export produces loadable f16 plus Q4_K_M files.

Words a new reader needs: QLoRA means training a frozen 4-bit base model plus small trainable side weights. LoRA rank (r=32) is the size of those side weights. Mamba is the non-attention part of this model family; its `out_proj` weight cannot be 4-bit quantized. T4 / Ampere / RTX 3090 are GPU types with different math support (fp16 everywhere, bf16 only on newer cards). GGUF is the file format for running the merged model outside Python. GHCR is GitHub's container storage. Smoke means a 5-step trial on 400 rows.

## Analysis
What is wrong, missing, or risky, worst first:

1. **The 3B training recipe does not transfer to a 90M reasoning model.** r=32, alpha=16, lr=2e-4, paged_adamw_8bit, NF4 4-bit base, and the `q/k/v/o/in/gate/up/down_proj` target list were picked for a 3B instruction model. On a 90M model r=32 is proportionally ~30x larger, so the side weights stop being "small" — overfitting and wasted capacity are likely. 4-bit quantization on 90M saves ~300 MB absolute while adding the exact fp16 instability the README already warns about for Mamba math. A full (non-quantized) or plain-LoRA run may be cheaper and more stable, but the concept assumes QLoRA carries over unchanged.
2. **Hard-coded 3B assumptions will reject or misconfigure Tiny.** `config.py` *requires* `bnb_skip_modules` to contain both `out_proj` and `lm_head` (the `lm_head` rule cites vocab size 65537, a 3B fact). Tiny-R may have a different vocab size, different layer names, or no `lm_head` misalignment problem — the validator will then force a wrong setting or block a correct one. `model.py` assumes the tokenizer ships a chat template and that `out_proj`/`conv1d` must never get LoRA; Tiny-R is a reasoning (`-R`) model whose chat/reasoning template, special tokens, and Mamba/attention mix must be re-verified, not assumed.
3. **Dataset size vs. model size is inverted.** The full corpus is ~42k rows (20k redteam + 8k exploitdb + 6k + 6k + rest). That is reasonable for 3B with 1 epoch. For a 90M model it is large enough to memorize, especially short Linux/Debian command rows. The concept keeps all 7 datasets with no re-capping, no length re-check, and no plan for reasoning traces: the `kimi-cyber-reasoning` rows and Tiny-R's expected think-then-answer format may mismatch the current `build_messages()` + chat-template rendering, producing long rows that get dropped by `max_len` or destabilize fp16.
4. **Two GPUs, two precisions, and now two models means config sprawl.** Today there are already two configs (Ampere bf16 / 2048 tokens, T4 fp16 / 1024 tokens). Adding Tiny naively doubles that to four. A 90M model fits in memory on either card even without 4-bit, so the T4-vs-3090 split may no longer be needed — but nobody has confirmed that, and the Makefile (`CONFIG`/`T4CONFIG`, `smoke`/`smoke-t4`/`train`/`train-t4`) plus `notebooks/run.ipynb` auto-select logic will need a naming rethink either way.
5. **Docker + GHCR is the largest new work, and the base-image choice is undecided.** There is no Dockerfile today; `pyproject.toml` pins `torch==2.11.0`, `transformers==5.20.2`, `bitsandbytes==0.50.2`. A CUDA base must match torch's CUDA build and carry both sm_75 (T4) and sm_86 (3090) kernels or one target fails with "no kernel image available" (a known README failure). bitsandbytes + Mamba fallback inside Docker on each arch is untested. The image will be ~8–12 GB; building and pushing it on every GitHub push burns CI minutes and storage unless tagged and cached carefully. CI today is three light CPU jobs (ruff, pytest, mypy, dry-run resolve) — a GPU smoke and a registry push are entirely new job types needing `packages: write` permission, login, tag rules, and a decision on whether pull requests also push.
6. **The verification bar is weaker than it looks.** "Finite loss + GGUF loads" does not mean the model learned anything: a 90M model can finish with finite but flat or degraded loss, and `llama.cpp` may not yet support the Tiny-R architecture, so "loads" can fail for converter reasons unrelated to training. Eval today reports per-row loss and worst offenders; there is no quality gate (no perplexity delta, no held-out sample check, no reasoning-format check), so a green run can still be a useless model.
7. **Newcomers cannot follow the current story.** README, configs, Makefile, and code are dense with unexplained terms (NF4, paged_adamw_8bit, gradient checkpointing, Arrow cache, SDPA vs flash-attention, smoke vs full). The concept adds Docker, RunPod, GHCR, and Tiny-R reasoning without a plain-English page saying what changed, which config to use on which GPU, and what to rent (3090 VRAM, disk, expected hours).

## Alternatives Weighed
* **Keep QLoRA 4-bit for Tiny (concept default) vs. full finetune or plain fp16/bf16 LoRA without bitsandbytes.** Rejected blind carryover: at 90M, 4-bit saves little and risks the documented fp16 Mamba instability. Draft must test full or non-quantized LoRA as the baseline and keep 4-bit only if it proves more stable or needed for T4.
* **Reuse r=32 / lr=2e-4 / 1 epoch unchanged vs. smaller rank + retuned lr.** Rejected unchanged: r=32 on 90M is proportionally large; keep r=8–16 candidates and a lower-lr fallback (1e-4, already the documented T4 fallback) with the FiniteLossCallback as the stop rule.
* **Four configs (3B×2 + Tiny×2) vs. one Tiny config vs. two Tiny configs.** Rejected four as sprawl: if Tiny fits both cards without quantization, one Tiny config replaces the pair. Keep the 3B files untouched but document them as legacy; add two Tiny files only if T4 memory forces shorter lengths/smaller caps.
* **One Dockerfile for both GPUs vs. per-GPU images.** Rejected per-GPU images: doubles build/push/test burden. One CUDA image carrying both compute capabilities is the default, with per-GPU images only as fallback if kernel or size problems force it.
* **Push to GHCR on every push vs. on tags/main only.** Rejected every-push: multi-GB pushes on each commit waste time and storage. Push on version tags (and optionally main), build-only on pull requests.
* **Same 7 dataset caps vs. re-capped Tiny corpus.** Rejected identical caps without review: short command datasets dominate per-token learning at 90M; expect cap reductions (especially redteam 20k and exploitdb 8k) after a first full-run loss/overfit read.
* **GGUF Q4_K_M for Tiny vs. f16-only export.** Rejected f16-only: user states GGUF support is mandatory, so both f16 and Q4_K_M must pass in this pass. If converter support for the Tiny hybrid arch is missing, the draft must pin or patch `llama.cpp` under `export.llama_cpp_dir` rather than deferring quantization.
* **Drop 3B entirely vs. keep side-by-side.** Rejected deletion in this pass: deleting 3B configs, Makefile targets, and notebook branches in the same change as adding Tiny/Docker/GHCR makes failures hard to attribute. Mark 3B legacy, remove later.
